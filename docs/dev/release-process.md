# Процесс релизов

Этот документ описывает, как в Protocol: Bunker собираются релизные артефакты и какие команды используются для упаковки проекта под разные платформы.

## Общая идея

Релизный процесс в проекте отделён от обычного локального dev-запуска.

Во время разработки обычно достаточно:
- `pnpm dev`
- `pnpm build`
- `pnpm typecheck`

Для релизов используются отдельные команды упаковки, которые собирают готовые артефакты под нужную платформу.

## Основные команды

Сборка релизов под Windows:

`pnpm pack:win`

Сборка Windows EXE-варианта:

`pnpm pack:win-exe`

Сборка релизов под Linux x64:

`pnpm pack:linux`

Сборка релизов под Linux ARM64:

`pnpm pack:linux:arm64`

## Что обычно происходит во время сборки релиза

В общем виде релизная сборка включает:
- подготовку и синхронизацию ресурсов;
- production-сборку нужных частей проекта;
- упаковку артефактов под выбранную платформу;
- подготовку portable или installable-вариантов, если они предусмотрены текущим сценарием сборки.

Точная внутренняя реализация может меняться, но смысл один: из исходников репозитория собирается готовый пакет, который можно публиковать как релизный артефакт.

## Основные типы артефактов

В зависимости от платформы и текущего релизного сценария проект может собирать разные варианты поставки.

### Windows

Обычно используются такие варианты:
- setup-версия;
- portable-вариант;
- архивированный EXE-вариант.

### Linux

Обычно используются такие варианты:
- public-сборка;
- server-сборка;
- варианты под разные архитектуры.

### Android

Android-релизы ведутся отдельно и могут публиковаться в отдельном репозитории релизов.

### macOS

Поддержка может находиться в разработке или быть ограниченной в зависимости от текущего состояния проекта.

## Когда использовать какую команду

### `pnpm pack:win`

Используется для основной упаковки Windows-релизов.

### `pnpm pack:win-exe`

Используется, если нужен отдельный EXE-формат поставки.

### `pnpm pack:linux`

Используется для Linux x64.

### `pnpm pack:linux:arm64`

Используется для Linux ARM64.

## Рекомендуемый порядок перед релизной сборкой

Перед упаковкой релиза полезно пройти базовый набор проверок:

1. Установить зависимости, если окружение поднималось заново  
   `pnpm install`

2. Проверить типы  
   `pnpm typecheck`

3. Проверить локализацию, если были изменения в UI или текстах  
   `pnpm locale:audit`  
   `pnpm locale:check`

4. Запустить интеграционные тесты, если релиз затрагивает сетевую, серверную или критичную игровую логику  
   `pnpm test:integration`

5. Собрать проект целиком  
   `pnpm build`

6. После этого запускать нужную `pack:*` команду

Такой порядок не обязателен в каждом случае, но обычно помогает заранее отловить типичные проблемы до упаковки артефактов.

## Что проверять после сборки

После релизной сборки полезно убедиться, что:
- артефакт действительно создался;
- нужный формат упаковки получен;
- приложение запускается;
- базовый сценарий входа в игру работает;
- клиент подключается к серверу;
- основные UI-сценарии не сломаны;
- если релиз затрагивал стриминг, viewer/control и overlay-сценарии тоже проверены.

Если для ручной проверки используется отдельный checklist, его лучше поддерживать отдельно в `docs/internal/qa-checklist.md`.

## Что может потребовать отдельного внимания

Релизная сборка чаще всего требует дополнительной проверки, если были изменения в:
- упаковочных скриптах;
- путях к ресурсам;
- иконках, ассетах и локалях;
- server/client build flow;
- portable-вариантах;
- platform-specific логике;
- streamer/viewer/control-сценариях;
- установке или обновлении сборки.

## Практический принцип

`build` отвечает за то, что проект собирается.

`pack:*` отвечает за то, что проект упаковывается в релизный артефакт под конкретную платформу.

Это разные этапы, и их лучше не смешивать:
- если нужно проверить кодовую целостность — сначала `build`, `typecheck`, тесты;
- если нужен итоговый релизный файл — затем `pack:*`.

## Примечание

Релизный процесс может меняться по мере развития проекта: состав артефактов, названия пакетов, платформенные варианты и внутренняя упаковка не обязаны оставаться неизменными. Если меняется релизный pipeline, этот документ тоже стоит обновлять вместе с ним.
